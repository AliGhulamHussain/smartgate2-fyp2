1. Project summary

SmartGate is a web platform that records attendance automatically using face recognition. A camera at a gate (a laptop or tablet running the Gate Kiosk screen) looks at the person, recognises who they are, and records a check-in or check-out. The system works out whether the person was late, who is inside the building right now, and builds a daily attendance report. When a face is not recognised, a photo is saved and an alert is raised for the administrators.

It is multi-tenant: many organisations (schools, universities, offices) can use the same installation, and each organisation sees only its own data.

What the system does (MVP scope)

Organisations and users

Sign-up for a new organisation, login, and five user roles with different permissions.

Attendance policy

Each organisation sets its working hours, grace minutes, working days and timezone.

Employees and gates

Add and manage employees and the physical gates (entry, exit or both).

Face enrollment

Capture a person's face through the webcam and store it as numbers, not as a photo.

Automatic check-in/out

The kiosk recognises a face and records attendance, lateness and early leave.

Live presence and reports

Who is inside now, daily reports, history and a 7-day trend chart.

Unknown-face alerts

Strangers are photographed, stored and listed for review by admins and managers.

Dashboard and kiosk

A React web dashboard for administration and a full-screen kiosk for gates.

Deliberately left out of the MVP: multiple shifts, payroll and leave management, manual attendance corrections, and exports.

4. System architecture

SmartGate has seven running parts: a React frontend, one API Gateway, four backend services, and two data stores (PostgreSQL and Redis) that run inside Docker.

Why 127.0.0.1?The services listen only on the local machine address, so nothing outside the computer can call them directly. The only way in from the browser is through Vite and the gateway.

Design rules that hold the system together

  • The browser only talks to the gateway. Services are never called directly by the frontend.
  • Each service owns its own data. No service reads another service's tables. If Recognition needs to know whether an employee exists, it asks the Attendance API.
  • No cross-schema foreign keys. Services store each other's IDs (e.g. employee_id) as plain values.
  • Internal endpoints stay internal. POST /internal/punch exists on Attendance but the gateway does not forward it; it needs a shared secret key.
  • Every query is scoped to the caller's organisation.

5. Docker

Docker runs programs in containers: isolated, pre-packaged environments that include the program and everything it needs. Instead of installing PostgreSQL, pgvector and Redis on Windows by hand, the project downloads ready-made images and runs them with one command. This means the database is set up the same way on every computer.

Docker Compose reads docker-compose.yml and starts all the containers it describes together.

What is in docker-compose.yml

ContainerImagePort (computer → container)Data stored inHealth check
smartgate-postgrespgvector/pgvector:pg16 (PostgreSQL 16 with pgvector built in)5433 → 5432Docker volume pgdatapg_isready every 5 s
smartgate-redisredis:7-alpine, with append-only persistence on6379 → 6379Docker volume redisdataredis-cli ping every 5 s
  • Volumes (pgdata, redisdata) are storage areas managed by Docker. They keep the data when containers are stopped or restarted. Data is only lost if the volume is deleted (for example with docker compose down -v).
  • Network smartgate connects the two containers.
  • First start: when the pgdata volume is new, PostgreSQL automatically runs db/init.sql, which creates the schemas, tables, roles and permissions.
  • restart: unless-stopped makes the containers come back automatically when Docker Desktop starts.
  • Port 5433 is used on the computer (instead of PostgreSQL's usual 5432) so it does not clash with any PostgreSQL already installed on Windows.
What runs in Docker and what does notOnly PostgreSQL and Redis run in Docker. The gateway, the four services and the frontend run directly on Windows with Node.js, which makes development and debugging easier. The compose file notes that the Node services can be added as containers later.

7. API Gateway (port 4000, gateway/)

The gateway is the single entry point of the backend. The frontend sends every request to it, and it decides where the request goes. It contains no business logic and no database connection; it only checks and forwards.

What happens to each request

  1. Origin check. If the request comes from a browser page other than http://localhost:5173, it is refused with 403. This stops other websites from using a logged-in user's session.
  2. CORS and headers. CORS is allowed only for the frontend origin. Responses are marked Cache-Control: no-store.
  3. Strip identity headers. Headers like x-user-id, x-organization-id, x-user-role and x-internal-key sent by the client are deleted, so nobody can pretend to be another user or service.
  4. Login check (all routes except signup, login, refresh, logout). The gateway takes the Authorization: Bearer <token> header and asks the Auth Service /api/auth/me whether it is valid. Invalid → 401/403; Auth down → 503.
  5. Routing. The URL prefix decides the target: /api/auth and /api/users → Auth, /api/attendance → Attendance, /api/recognition → Recognition, /api/alerts → Alerts. The full path and body are forwarded unchanged.
  6. Errors. If a service can't be reached the gateway returns 502 with a clear message; unknown routes return 404. Timeouts are 10–15 seconds.
Defence in depthThe gateway's login check is a first filter. Each service still verifies the token again itself and checks the user's role and organisation, so a service is safe even if a request somehow bypasses the gateway.

Files: server.js (setup, origin check, header stripping), routes/api.js (route table and proxies), middleware/auth.js (token check via Auth).

8. Auth Service (port 4001, schema auth)

Handles who you are and which organisation you belong to.

Responsibilities

  • Organisation sign-up: creates the organisation and its first org_admin user together in one database transaction (both succeed or neither does). Sign-up is rate-limited to prevent abuse.
  • Login: checks the password against its bcrypt hash, then issues:
    • an access token (JWT, valid 15 minutes) returned to the app, kept only in memory;
    • a refresh token (valid 14 days) in an HttpOnly cookie that JavaScript cannot read. Only its hash is saved in the database.
  • Refresh: swaps an old refresh token for a new pair (token rotation), so a stolen old token stops working.
  • Logout and session revocation after security-sensitive changes (e.g. password or role changes).
  • /api/auth/me: returns the current user. The gateway and every other service use this to verify tokens.
  • User management: list, create and update users inside your own organisation only.
  • Blocks inactive users and suspended organisations.

Files: routes/auth.js (signup, login, refresh, logout, me), routes/users.js (team members), sessions.js (tokens, cookie and account checks), auth.js (checks the access token on each request), helpers.js, db.js.

9. Attendance Service (port 4002, schema attendance)

The core business logic: policies, employees, gates, check-ins and reports.

Policy

Each organisation has one policy: timezone, work start and end, grace minutes, working days and an auto-close time. Only org_admin can change it. All times are calculated in the policy's timezone.

Employees

  • Create, list, view and update. Only org_admin can create or edit; all roles can read.
  • Employee code must be unique inside the organisation (the same code may exist in another organisation).
  • Employees are never deleted, only deactivated, because attendance history points to them.
  • presence and face_enrolled cannot be edited by users: punches set presence, the Recognition Service sets face_enrolled.
  • The list supports search (name or code), filters (status, presence, department) and pagination.

Gates

Each gate has a name and a direction: entry (always check-in), exit (always check-out) or both (toggles: if outside, check in; if inside, check out). Gates are deactivated, never deleted.

Punch processing: the attendance rules

When the Recognition Service matches a face, it calls POST /internal/punch with the employee, gate and confidence. This endpoint needs the secret X-Internal-Key and is not reachable through the gateway.

  • Cooldown: a repeat punch for the same person within 180 seconds is ignored. The employee row is locked during processing, so five simultaneous punches record exactly one.
  • Late: only the first check-in of a working day is judged. Arriving more than grace_minutes after work_start is late, and the lateness is counted from work_start. Re-entries later in the day are normal. Weekends and holidays are never late.
  • Early leave: checking out before work_end on a working day is early_leave.
  • Every punch writes a row to attendance_logs and updates the employee's presence.
  • Daily summary: the first check-in of the day creates the daily_attendance row (present or late); each check-out updates the last check-out time and adds the minutes spent inside.
  • Forgotten check-outs: a background job runs every minute. After the auto-close time (or on the next day) it marks people as outside and sets that day to incomplete.
  • Ignored punches return a reason: cooldown, already_inside or not_inside.

Monitoring (read-only, all roles)

EndpointReturns

10. Recognition Service (port 4003, schema recognition)

Stores face data and decides whose face this is.

Privacy by designFace detection runs in the browser. The service only ever receives the 128-number descriptor, never a photo of an enrolled person. The only image it ever handles is an optional snapshot of an unknown face, which it passes on to Alerts.

Enrollment (org_admin)

  • Receives 3–10 face samples for an employee; new samples replace old ones.
  • Checks with the Attendance API that the employee exists, belongs to the organisation and is active.
  • Refuses (409) if the same face is already enrolled for a different employee.
  • Tells Attendance to set face_enrolled = true through an internal endpoint; if that fails, the samples are rolled back.
  • Deleting a face removes all samples and clears face_enrolled.

Identification (gate_operator, org_admin)

  1. The kiosk sends the face descriptor, the gate ID, liveness_passed (blink check result) and optionally a JPEG snapshot.
  2. If liveness is required and not passed → 400. The gate must be active and in the same organisation.
  3. pgvector search: computes the L2 (straight-line) distance between the descriptor and every sample in the organisation, and keeps the nearest sample per employee.
  4. Decision: a match needs distance ≤ match_threshold (0.5), and the best person must be at least 0.05 closer than the second-best person. Otherwise the result is no_match or ambiguous.
  5. Every attempt is saved in recognition_events.
  6. On a match: calls Attendance /internal/punch with confidence = 1 − distance, and returns the employee and attendance result to the kiosk.
  7. On no match with a snapshot: writes an event to the Redis stream smartgate:unknown-faces (at most one per gate every 30 seconds) and returns alert_queued. If Redis is down, identification still works.

Settings (org_admin)

match_threshold between 0.2 and 0.8 (lower = stricter), and liveness_required on/off.

Files: routes/faces.js, routes/identify.js, routes/settings.js, events.js (Redis stream producer), test/recognition.test.js.

11. Alerts Service (port 4004, schema alerts)

Handles unknown faces, notifications and the audit log.

Stream consumer

  • Joins the Redis consumer group alerts-service and reads events from smartgate:unknown-faces.
  • Validates each event, saves the JPEG into the snapshots folder (services/alerts-service/snapshots/) and stores only the file path in alerts.unknown_faces.
  • The alert ID is derived from the stream message ID, so processing the same message twice can never create a duplicate alert.
  • Queues one notification per recipient subscribed to unknown_face.
  • Bad messages are logged and dropped; other failures stay pending and are retried when the service restarts.

APIs

  • Unknown faces: list (with counts per status and filters), view, view snapshot, and review (new → reviewed or dismissed, with a note and who reviewed it).
  • Snapshots are only served through the API with a valid token; the file path is never revealed.
  • Recipients: email addresses and the alert types they want.
  • Notifications log and audit log (reviews and recipient changes, with the acting user).

Files: consumer.js, routes/unknown-faces.js, routes/recipients.js, routes/history.js, test/alerts.test.js.

12. Frontend (frontend/, localhost:5173)

A single-page React app with two faces: the admin dashboard and the gate kiosk.

How it connects to the backend

  • The app calls /api/... on its own address. The Vite server forwards those calls to the gateway at port 4000. This keeps the refresh cookie on the same site and makes the gateway's origin check pass.
  • The access token is kept in memory only. On page reload, the app uses the refresh cookie to restore the session. If any request gets 401, it refreshes once and retries automatically.
  • Navigation uses hash URLs (e.g. #/employees), handled by a tiny router in src/router.js.
  • The menu changes by role, matching what the backend allows.

How the face AI works in the browser

src/face.js loads three neural network models from /models (copied from node_modules at build time):

  1. Tiny Face Detector – finds where the face is in the camera frame.
  2. Face Landmark 68 – finds 68 points on the face (eyes, nose, mouth). The eye points are also used for the blink check.
  3. Face Recognition Net – turns the face into the 128-number descriptor.

The face libraries are only loaded on the kiosk and enrollment screens (code splitting), so the rest of the dashboard stays light.

The kiosk, step by step

  • Shows a live clock and the camera feed.
  • Needs the same person in 3 consecutive frames before acting.
  • Runs an adaptive blink check using the eye aspect ratio (how open the eyes are).
  • Averages the descriptors, takes a small JPEG of the face, and sends them to /api/recognition/identify.
  • Shows a result card: Welcome, Late, Goodbye, Already recorded or Not recognised.
  • Ignores the person it just identified while they walk away.

Other files: api.js (fetch wrapper with refresh-and-retry), auth.jsx (session state), ui.jsx (buttons, tables, modals, toasts), index.css (design tokens), snapshot.jsx (loads alert photos with the token).

13. End-to-end flows

A. Setting up an organisation

  1. Open http://localhost:5173 and sign up. Auth creates the organisation and the first admin.
  2. In Settings, set the attendance policy (timezone, hours, grace minutes, working days).
  3. Add gates (e.g. "Main Gate", direction both).
  4. Add employees, then enroll each employee's face.
  5. Open the kiosk for a gate on the device at that gate (logged in as a gate operator or admin).

B. Logging in

  1. Browser → Vite → Gateway → Auth: POST /api/auth/login with email and password.
  2. Auth checks the bcrypt hash, creates a session, returns the 15-minute access token and sets the 14-day refresh cookie.
  3. Every later request carries Authorization: Bearer <token>. The gateway confirms it with Auth before forwarding.
  4. When the token expires, the app calls /api/auth/refresh automatically and retries.

C. Enrolling a face

  1. Admin opens an employee and starts enrollment. The webcam turns on.
  2. face-api captures 5 samples, checking each is consistent with the first.
  3. The browser sends only the 5 × 128 numbers: PUT /api/recognition/employees/:id/faces.
  4. Recognition checks the employee with Attendance, makes sure the face isn't already someone else's, and stores the samples in pgvector.
  5. Recognition tells Attendance (internal call) to set face_enrolled = true.

D. A known employee arrives at the gate

  1. Kiosk detects a face in 3 frames in a row and the person blinks.
  2. Kiosk sends descriptor + gate ID + liveness result + snapshot to POST /api/recognition/identify (via Vite and the gateway).
  3. Recognition finds the nearest employee using pgvector. Distance 0.32 ≤ 0.5 and clearly better than the next person → match.
  4. Recognition calls Attendance POST /internal/punch with the secret key.
  5. Attendance locks the employee row, checks the cooldown, sees the employee is outside → check-in. It is 09:25 with a 09:00 start and 10 grace minutes → late by 25 minutes.
  6. Attendance writes the log, sets presence to inside, and creates today's daily row with status late.
  7. The result travels back; the kiosk shows "Late – 25 min". The dashboard's Presence and Overview update on their next refresh.

E. An unknown person arrives at the gate

  1. Kiosk sends the descriptor and a JPEG snapshot to identify.
  2. Recognition finds no employee within the threshold → no_match. The event is saved.
  3. If this gate hasn't raised an alert in the last 30 seconds (checked with a Redis key), Recognition adds an event with the snapshot to the Redis stream.
  4. The kiosk shows "Not recognised".
  5. The Alerts Service reads the event, saves the JPEG to the snapshots folder, creates an unknown_faces row and queues notifications for subscribed recipients.
  6. An admin or manager opens Alerts, sees the photo, and marks it reviewed or dismissed. The review is written to the audit log.

F. Someone forgets to check out

  1. The Attendance background job runs every minute.
  2. After the policy's auto-close time (23:30 by default), anyone still inside is set to outside.
  3. That day's record becomes incomplete. No fake check-out is written, so the history stays honest.

18. How to run

Requirements: Docker Desktop, Node.js (v24 used), Google Chrome or Edge, a webcam.

First time on a new computer

  1. Copy .env.example to .env and fill in JWT_SECRET and INTERNAL_SERVICE_KEY with long random strings.
  2. Run npm install in gateway, each folder in services, and frontend.

Every time

1. Start Docker Desktop
2. docker compose up -d                                  (in the project folder)
3. cd services\auth-service;        npm start           (terminal 1, port 4001)
4. cd services\attendance-service;  npm start           (terminal 2, port 4002)
5. cd services\recognition-service; npm start           (terminal 3, port 4003)
6. cd services\alerts-service;      npm start           (terminal 4, port 4004)
7. cd gateway;                      npm start           (terminal 5, port 4000)
8. cd frontend;                     npm start           (terminal 6, port 5173)
9. Open http://localhost:5173
Use localhost, not 127.0.0.1Browsers only allow camera access and the refresh cookie on localhost. npm start in the frontend builds the optimised version (about 2.8 s to load); npm run dev is for editing and is slower.

Stop: Ctrl+C in each terminal, then docker compose down (data is kept).

Known limitations

To be tuned with real camerasThe match threshold (0.5), margin (0.05) and blink thresholds are starting values. So far the kiosk has only been tested with a simulated camera.
  • No email is actually sent yet: notifications are queued, waiting for an email (SMTP) sender. Only unknown-face notifications are produced.
  • The blink check stops printed photos, but not a video replay or a modified client.
  • Only one shift per organisation; overnight shifts are not supported.
  • Holidays have no screen or API yet; they can only be added in the database.
  • No automatic migration runner; migrations are applied by hand.
  • Audit log covers Alerts actions only.
  • Unknown-face snapshots are kept forever on disk.
  • Failed stream events are retried only when the Alerts Service restarts.
  • Face search compares against every sample in the organisation; fine for thousands of samples. For much larger organisations, an HNSW index (already prepared in init.sql as a comment) can be enabled.
  • Development database passwords are written in db/init.sql; a real deployment would use secrets.

Future work

  • Email sending; late-arrival, forgotten-checkout and daily-summary notifications.
  • Multiple shifts, leave management, manual corrections and report exports.
  • Stronger anti-spoofing (depth or challenge-response).
  • Running all services in Docker for one-command deployment.
