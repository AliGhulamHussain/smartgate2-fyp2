2. PROJECT PURPOSE AND MVP
--------------------------

SmartGate is a multi-tenant, face-recognition-based attendance and access
monitoring platform for schools, universities, offices, and similar
organizations.

MVP features:

- Organization registration and tenant isolation
- Role-based organization users
- One attendance policy/shift per organization
- Employee management
- Gate/location management
- Face enrollment using 128-dimensional embeddings
- Employee recognition
- Automatic check-in/check-out
- Late-arrival calculation
- Current presence monitoring
- Daily attendance summaries
- Unknown-face records and alerts
- React administration dashboard and gate kiosk

Deferred from the MVP:

- Multiple shifts
- Payroll
- Complex leave management
- Manual attendance overrides
- Advanced schedules and exports

Do not expand scope unnecessarily.

4. ARCHITECTURE
---------------

Frontend (planned, port 5173)
    -> API Gateway (127.0.0.1:4000)
        -> Auth Service (127.0.0.1:4001)
        -> Attendance Service (127.0.0.1:4002)
        -> Recognition Service (planned)
        -> Alerts Service (planned)
    -> PostgreSQL/pgvector (Docker host port 5433)
    -> Redis (Docker host port 6379)

Normal frontend requests must go through the API Gateway. Internal endpoints,
especially POST /internal/punch, must not be exposed by the gateway.

Each service has its own restricted PostgreSQL account and schema. A service
must not query another service's schema. Use REST for synchronous communication
and Redis Streams only for appropriate asynchronous workflows.

Recognition must not write Attendance tables. After a successful match, it must
call the Attendance Service's internal POST /internal/punch endpoint.

Live isolation tests confirmed each role can access its own schema and receives
permission denied for another service's schema. None is a superuser or can
create roles/databases.

Important Attendance table details:

attendance.org_policies:

- organization_id UUID primary key
- timezone VARCHAR(50), default Asia/Karachi
- work_start TIME, default 09:00
- work_end TIME, default 17:00
- grace_minutes INT, default 10
- working_days SMALLINT[], ISO weekdays
- auto_close_time TIME, default 23:30
- updated_at TIMESTAMPTZ

attendance.employees:

- id UUID primary key
- organization_id UUID
- employee_code VARCHAR(50)
- full_name VARCHAR(100)
- email VARCHAR(150), nullable
- phone VARCHAR(20), nullable
- department VARCHAR(100), nullable
- designation VARCHAR(100), nullable
- status: active or inactive
- presence: inside or outside
- face_enrolled BOOLEAN
- created_at and updated_at
- unique (organization_id, employee_code)

attendance.gates:

- id UUID primary key
- organization_id UUID
- name VARCHAR(80)
- direction: entry, exit, or both
- created_at
- unique (organization_id, name)

Known gap: gates do not have an active/inactive column even though the roadmap
requests gate deactivation. Make an explicit migration decision when gates are
implemented; do not invent a column only in code.

attendance.attendance_logs:

- Raw check-in/check-out events
- Organization, employee and optional gate IDs
- action: check_in/check_out
- status: on_time/late/normal/early_leave
- late_by_minutes, confidence, source and logged_at

attendance.daily_attendance:

- One row per employee/work date
- first_check_in, last_check_out, total_minutes and late_by_minutes
- status: present/late/absent/holiday/weekend/incomplete
- unique (employee_id, work_date)

Recognition embeddings use vector(128). The documented query uses L2 distance
with the <-> operator and a default threshold of 0.6. Do not change the vector
dimension, distance metric, or threshold direction without inspecting the
matching implementation.

There is no migration system yet. db/init.sql runs automatically only when a
new PostgreSQL volume is initialized. Future schema changes need explicit,
repeatable migration files; changing init.sql alone does not update an existing
volume.

10. ATTENDANCE SERVICE — IMPLEMENTED POLICY SLICE
-------------------------------------------------

Address: http://127.0.0.1:4002

Implemented endpoints:

- Direct GET /health
- Gateway GET /api/attendance/policy
- Gateway PUT /api/attendance/policy

Security:

- Uses ATTENDANCE_DATABASE_URL and attendance_svc
- Independently verifies bearer sessions through Auth /api/auth/me
- Does not trust client identity headers
- Uses authenticated user organization_id
- Users without an organization receive 403
- Organization users may read policy
- Only org_admin may create/update policy
- super_admin has no organization scope and is currently rejected

Policy behavior:

- GET returns 404 when no policy exists
- PUT requires all supported fields and rejects extras
- PUT uses parameterized INSERT ... ON CONFLICT UPDATE
- updated_at is refreshed
- Validates IANA timezone
- Accepts HH:MM or HH:MM:SS and normalizes time
- grace_minutes must be integer 0-1440
- working_days must be unique ISO weekdays 1-7
- work_start and work_end must differ

Request example:

{
  "timezone": "Asia/Karachi",
  "work_start": "09:00",
  "work_end": "17:00",
  "grace_minutes": 10,
